# Shamrai Backup And Restore Drill

This runbook covers the canonical Shamrai VDS deployment only:

- Server: `root@82.147.67.245`
- App path: `/opt/shamrai-mini-app`
- Docker Compose project: `shamrai`
- Preview health: `http://127.0.0.1:8082/api/health`

Keep one canonical preview deployment. Do not create a second app path, Compose project, or preview port to solve conflicts.

## What Is Backed Up

Postgres is the recovery source of truth. The nightly job creates a custom-format `pg_dump`, encrypts it with `age`, stores a manifest with table counts and hashes/sizes for both plaintext and encrypted artifacts, signs the exact manifest bytes with a separate Ed25519 key, and removes the unencrypted temp dump.

Redis is not restored from backup. The restore drill starts Redis clean and verifies `redis-cli ping`; critical outbox, payments, subscriptions, users, delivery permissions, and payment states live in Postgres.

Retention:

- `14` daily encrypted backups in `/opt/shamrai-mini-app/db-backups/daily`
- `8` weekly encrypted backups in `/opt/shamrai-mini-app/db-backups/weekly`
- `latest.dump.age`, `latest.manifest.json`, and `latest.manifest.sig` symlinks point to the newest signed daily backup

First create the operator identity if the exact path does not exist. Run this only on the operator machine; never paste or print the private identity:

```powershell

```

Use the public `age1...` recipient printed by `age-keygen` as `SHAMRAI_BACKUP_AGE_RECIPIENT`. The identity file is outside the repository and must never be committed.

Bootstrap the separate Ed25519 signing key explicitly on the VDS before installing S3 credentials. The private key is generated by OpenSSL only inside a root-only VDS pipeline and is encrypted directly with `systemd-creds`; the installer has no parameter, environment variable, stdin field, SCP path, or local file for private signing-key bytes. A repeated bootstrap reuses the existing encrypted credential and never rotates it.

For the first bootstrap, make sure no public trust anchor is supplied. The pinned SSH host key authenticates the returned non-secret public key:


- the current process as `SHAMRAI_BACKUP_MANIFEST_SIGNING_PUBLIC_KEY_BASE64=<returned-base64-ed25519-spki-der>`;

- `/opt/shamrai-mini-app/ops/backup.env` only through `configure-shamrai-backups.ps1`, never by manually editing the file.

If an encrypted signing credential already exists, bootstrap prints its existing public key; if a different public key is supplied, it fails closed. ## Optional Off-Host S3-Compatible Copy

Off-host upload is opt-in. With no `OffHostS3Bucket`/`SHAMRAI_BACKUP_S3_BUCKET`, backup behavior remains local-only and cron invokes `backup-db.sh` directly. A bucket enables the protected path: the local ciphertext and schema-v3 manifest are created, the exact manifest bytes are signed and immediately verified, and the signature is committed last. S3 upload and `HeadObject` verification run strictly as ciphertext → manifest → signature; only the `.manifest.sig` object is a remote commit marker. Missing runtime credentials, signing failures, or any remote error still runs normal local retention, preserves completed local files, and then returns the saved non-zero status.

Safe command-generation check (no SSH, VDS, Docker, or S3 request):

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\configure-shamrai-backups.ps1 `
  -DryRun `
  -BackupAgeRecipient age1replacewithpublicrecipient `
  -OffHostS3Bucket example-backups `
  -OffHostS3Prefix shamrai `
  -OffHostS3EndpointUrl https://s3.example.invalid `
  -OffHostS3Region us-east-1 `
  -ManifestSigningPublicKeyBase64 MCowBQYDK2VwAyEA11qYAYKxCrfVS/7TyWQHOg7hcvPapiMlrwIaaPcHURo=
```

The public key in the dry-run example is an RFC 8032 test-vector key and must not be used as a production trust anchor. To install only the non-secret remote configuration, pass the same parameters without `-DryRun` and use the real public age recipient and public signing key. The configure script never accepts or forwards S3 credentials or signing private-key bytes. With a bucket, it requires all encrypted systemd credentials above and installs the service/timer. It decrypts only inside a pipeline to derive the public key and fails before changing the schedule if the key pair differs or OpenSSL, AWS CLI, or `systemd-creds` is unavailable.

Custom credential wrappers are disabled for the protected S3 release path. The generated root-owned systemd wrapper exports AWS credentials for its child and exposes only the credential-file path for the signing key:

```text
AWS_ACCESS_KEY_ID=<runtime-only-access-key-id>
AWS_SECRET_ACCESS_KEY=<runtime-only-secret-access-key>
AWS_SESSION_TOKEN=<optional-runtime-only-session-token>
SHAMRAI_BACKUP_MANIFEST_SIGNING_PRIVATE_KEY_FILE=/run/credentials/shamrai-db-backup.service/manifest_signing_private_key
```

Use a dedicated bucket principal limited to `s3:PutObject`, `s3:GetObject` (also used by `HeadObject`), and prefix-scoped `s3:ListBucket`. Do not grant `s3:DeleteObject`, lifecycle administration, bucket policy administration, or Object Lock bypass to the backup process. Never enable shell tracing (`set -x`) around the credential injection wrapper.

Integrity sequence:

1. Create the plaintext custom-format dump in a mode-`0700` temporary directory.
2. Encrypt it with `age` into a temporary `.dump.age`.
3. Compute the encrypted SHA-256 and byte length, then create manifest schema v3 containing `backup_id`, artifact names, S3 coordinates, and the SHA-256 of the trusted Ed25519 public key.
4. Sign the exact UTF-8/LF manifest bytes, require a 64-byte Ed25519 signature, and immediately verify it with the configured public key.
5. Commit the local ciphertext, manifest, and signature in that order; weekly copies, `latest.*` links, and pruning operate on all three files.
6. Upload and verify ciphertext, manifest, and signature in that order. Restore selection considers only the signature a commit marker.

`backup-db.sh` takes a non-blocking exclusive `flock` before timestamp generation. A concurrent cron/manual writer is rejected instead of sharing object names or overwriting a manifest/ciphertext pair.

The signature protects provenance even though the `age` recipient and S3 writer credentials are not signing authorities. The private Ed25519 key is a separate systemd credential and is never uploaded. Hashes still detect artifact corruption; provider audit logs, versioning, and immutable retention remain mandatory.

Off-host retention is provider-side; the backup script deliberately has no remote delete permission. Configure and periodically audit:

- bucket versioning before the first upload;
- Object Lock/WORM or an equivalent immutable retention policy where the provider supports it;
- lifecycle retention that meets the recovery policy (for example, current daily objects for at least 35 days and non-current versions for at least 90 days);
- lifecycle rules that keep each `.dump.age`, matching `.manifest.json`, and `.manifest.sig` for the same duration;
- a separate administrative identity for retention changes and restores.

### S3 retention and writer-capability gate

Before an S3 restore drill or release gate can pass, run `scripts/verify-shamrai-s3-retention.ps1`. The verifier first performs these read-only administrative checks with a dedicated audit identity:

- `GetBucketVersioning` and requires `Status=Enabled`;
- `GetObjectLockConfiguration` and requires default `COMPLIANCE` retention of at least `35` days;
- `GetBucketLifecycleConfiguration` and requires unconditional coverage of the configured prefix, with current expiration at least `35` days and noncurrent expiration at least `90` days;
- `GetBucketPolicy` and reads the effective provider-side resource policy twice: before and after writer probes. Any change during verification fails closed.

The verifier also parses the exact writer identity policy supplied at runtime. Every `Allow` must be limited to `s3:PutObject`, `s3:GetObject`, or conditionally prefix-scoped `s3:ListBucket`, and all three actions must cover the generated `<prefix>/daily/*` objects. Wildcard actions, delete, Object Lock bypass, retention mutation, lifecycle administration, and bucket administration grants fail the gate. A narrower child-prefix lifecycle rule also fails if it can expire any current or noncurrent backup earlier than the required minimum.

The identity-policy document alone is not accepted as proof of effective permissions. The release gate currently supports only AWS-managed default S3, STS, and IAM endpoints. With the actual writer credential, the verifier calls STS `GetCallerIdentity`, normalizes a supported IAM user/role identity, and requires the live bucket policy to bind four strict `Deny` rules to that exact stable principal:

- `NotAction` is exactly `PutObject`, `GetObject`, and `ListBucket`, while `Resource` is exactly the bucket and `bucket/*`; this denies every other S3 action even if another identity policy grants it;
- `PutObject` and `GetObject` use `NotResource=<bucket>/<prefix>/*`, denying those two otherwise-allowed actions outside the configured prefix;
- `ListBucket` is denied by `StringNotLike` unless `s3:prefix` is exactly `<prefix>` or `<prefix>/*`;
- a separate `Null` rule denies `ListBucket` when the request omits `s3:prefix`.

The verifier then uses the separate audit identity to call IAM `GetUser` or `GetRole`, `GetPolicy`, and `GetPolicyVersion`. The live writer must have a customer-managed permissions boundary whose default version contains the exact three prefix-scoped allows and five explicit denies: every non-backup action, object access outside the prefix, list access to other buckets, list access outside the prefix, and list requests without `s3:prefix`. It fetches both the bucket policy and permissions boundary again after the probes and rejects any hash, ARN, or default-version change.

The principal, action sets, resources, conditions, and `NotResource` are parsed strictly. Public `Principal="*"`, conditional admin denies, extra `NotAction` exceptions such as `sts:AssumeRole`, unsupported/federated principals, and missing-prefix gaps fail closed. Custom S3-compatible endpoints are deliberately rejected for a real release attestation until that provider has an authoritative identity-policy and permissions-boundary API. `SHAMRAI_BACKUP_S3_ENDPOINT_URL` and the reserved `SHAMRAI_BACKUP_S3_STS_ENDPOINT_URL` must both be empty for this AWS release gate; dry-run may still normalize example endpoints without making requests.

After the policy and identity binding checks, the verifier performs provider-neutral S3 capability probes with the same writer credential:

- `PutObject`, `GetObject`, and prefix-scoped `ListBucket` must succeed for one non-secret object under `<prefix>/daily/capability-probes/`, and the downloaded SHA-256 must match;
- `DeleteObject` for the current probe key must be rejected with a recognizable authorization denial;
- `DeleteObjectVersion` targets a random missing key and version under the allowed prefix and must be rejected with a recognizable authorization denial. It never targets the COMPLIANCE-locked probe version, because Object Lock could otherwise produce the same denial for an overprivileged writer;
- `PutObject`, `GetObject`, and `ListBucket` against a randomized outside-prefix path must each be rejected with a recognizable authorization denial;
- connectivity, timeout, invalid-credential, and other provider errors never count as proof that an operation is denied.

The positive probe object contains only a random probe identifier and remains protected by WORM/lifecycle retention; the writer intentionally cannot clean it up. If an outside-prefix write is unexpectedly permitted, the gate fails immediately and that small probe object may also remain until an administrator handles it. The attestation binds this design as `writer_effective_permission_evidence=live_aws_sts_iam_boundary_bucket_policy_v3+live_unconfounded_object_probes_v3`.

The same writer identity must also receive a recognizable `AccessDenied`/`Forbidden` response for these non-destructive live object-level administrative probes:

- `PutObjectRetention` and `PutObjectLegalHold` target a randomized key and version ID that the verifier never creates;
- `PutObjectAcl`, `PutObjectTagging`, and `DeleteObjectTagging` target the randomized missing key without `versionId`, so the probes test the base `s3:PutObjectAcl`, `s3:PutObjectTagging`, and `s3:DeleteObjectTagging` actions rather than their version-specific counterparts;
- `AbortMultipartUpload` targets that missing key with a randomized deliberately invalid upload ID.

Only an authorization denial passes. `NoSuchKey`, `NoSuchVersion`, `NoSuchUpload`, `Invalid*`, transport/provider failures, and command success all fail the probe. The verifier never sends a bucket-policy, lifecycle, Object Lock, versioning, ACL, or deletion mutation request; denial of those capabilities is proven by the live bucket policy and IAM permissions boundary bound to the STS-derived writer principal.

The non-secret attestation has schema version `3` and includes normalized storage coordinates; WORM/lifecycle evidence; the live bucket-policy hash and four-rule result; STS identity fingerprints; `writer_permissions_boundary_status=passed`, boundary ARN/policy hashes, version, and five-rule result; every writer/admin capability boolean; `writer_effective_permission_evidence=live_aws_sts_iam_boundary_bucket_policy_v3+live_unconfounded_object_probes_v3`; `writer_delete_object_version_probe_target=random_missing_key_and_version`; `writer_admin_probe_target=random_missing_object_resources+aws_iam_boundary_v4`; `writer_admin_capability_probe=passed`; `writer_policy_sha256`; and `writer_access_key_id_sha256`. Raw access-key IDs, secret keys, session tokens, policy bodies, and principal ARNs never appear in the attestation or console output. A failed real check removes any stale passed attestation before exiting non-zero.

In GitHub Actions, the same attestation must include `repository`, `workflow_run_id`, `workflow_run_attempt`, and `git_sha` captured from the GitHub runtime. The verifier rejects missing or malformed provenance while `GITHUB_ACTIONS=true`; outside Actions these four fields are empty. A production release must not accept a locally generated attestation: it must download the immutable artifact for the recorded workflow run through the GitHub API and require the repository, run attempt, and exact commit SHA to match the release.

`writer_policy_sha256` records the intended identity policy, while the AWS-returned bucket-policy hash, STS-derived stable-principal hash, and live IAM permissions-boundary hash prove the enforced limit. The boundary explicitly denies list access to other buckets and all non-backup actions, including role assumption. If any policy, boundary version, or writer principal changes, generate a new attestation before release.

In GitHub, create the protected Environment `shamrai-production-backup`, restrict deployment branches to the protected default branch, and require an operator reviewer. Store the following as **Environment secrets** (not repository variables and not files):

- `SHAMRAI_BACKUP_S3_AUDIT_ACCESS_KEY_ID` — separate read-only audit access key;
- `SHAMRAI_BACKUP_S3_AUDIT_SECRET_ACCESS_KEY` — matching audit secret key;
- `SHAMRAI_BACKUP_S3_AUDIT_SESSION_TOKEN` — optional audit session token;
- `SHAMRAI_BACKUP_S3_ACCESS_KEY_ID` — actual prefix-scoped backup-writer access key used by the VDS;
- `SHAMRAI_BACKUP_S3_SECRET_ACCESS_KEY` — matching writer secret key;
- `SHAMRAI_BACKUP_S3_SESSION_TOKEN` — optional writer session token;
- `SHAMRAI_BACKUP_S3_WRITER_POLICY_JSON` — exact JSON policy attached to the prefix-scoped backup writer.

Also place `SHAMRAI_SSH_PRIVATE_KEY` and `SHAMRAI_BACKUP_AGE_IDENTITY` in that protected Environment. Reuse the repository **Variables** `SHAMRAI_BACKUP_S3_BUCKET`, `SHAMRAI_BACKUP_S3_PREFIX`, and `SHAMRAI_BACKUP_S3_REGION`, and add the non-secret trust anchor `SHAMRAI_BACKUP_MANIFEST_SIGNING_PUBLIC_KEY_BASE64`. Keep both `SHAMRAI_BACKUP_S3_ENDPOINT_URL` and the reserved `SHAMRAI_BACKUP_S3_STS_ENDPOINT_URL` empty for the AWS-only safe release gate. The workflow itself rejects non-default-branch refs before secrets are made available. Do not create a repository file for any audit, writer, or signing private key. The weekly workflow passes credentials only through step environment variables, writes policy evidence to `$RUNNER_TEMP/shamrai-s3-audit/writer-policy.json` with mode `0600`, deletes it in the unconditional cleanup step, and uploads only redacted attestations.

Failure alerts are mandatory when off-host mode is enabled. Alert on a non-zero backup exit, the `shamrai-backup` syslog tag, or the absence of a newly committed remote `.manifest.sig` within 26 hours. Keep `/opt/shamrai-mini-app/ops/backup.log` under log rotation and route cron/monitoring failures to the on-call channel. A local success without a recent signed remote commit marker is a degraded backup, not a successful off-host backup.

## Weekly Restore Drill

Manual run from the operator machine:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run-shamrai-restore-drill.ps1
```

The script:

1. Locates the newest `.manifest.sig` as an untrusted provisional marker on the VDS, or under the off-host daily prefix when `-ArtifactSource S3` is explicit.
2. Downloads only the manifest and signature first and verifies their S3 size/hash metadata when applicable.
3. Verifies the Ed25519 signature over the exact manifest bytes before JSON parsing, then requires schema v3 and binds `created_at`, `backup_id`, filenames, bucket, prefix, and all three S3 keys to the selected bundle.
4. Fails closed if the newest marker is unsigned, corrupt, signed by another key, renamed, replayed under another timestamp, or missing a bundle member; it never silently falls back to an older backup.
5. Only after authentication, downloads the ciphertext, validates its signed hash/size, decrypts locally with `C:\Users\Sa1z1ngr0z\.config\age\shamrai-backup-identity.txt`, and validates the decrypted dump SHA-256.
6. Uploads the decrypted dump to a temporary `0700` stage under `/tmp` and starts a temporary Compose project named `shamrai-restore-drill-*` on localhost-only ports `18000` and `18082`.
7. Restores Postgres, compares signed table counts, verifies Redis, backend health, frontend HTML, and canonical production health.
8. Deletes the temporary Compose project, volumes, and stage unless `-KeepDrillProject` is passed. The S3 restore attestation records the signature object/hash, trusted public-key hash, algorithm, and `signature_verified=true`.

Use an explicit backup when needed:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run-shamrai-restore-drill.ps1 -BackupFile /opt/shamrai-mini-app/db-backups/daily/shamrai-db.YYYYMMDDTHHMMSSZ.dump.age
```

Preview selection of the newest off-host artifact without network access:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run-shamrai-restore-drill.ps1 `
  -DryRun `
  -ArtifactSource S3 `
  -OffHostS3Bucket example-backups `
  -OffHostS3Prefix shamrai `
  -OffHostS3EndpointUrl https://s3.example.invalid `
  -OffHostS3Region us-east-1
```

For a real drill, set the non-secret `SHAMRAI_BACKUP_MANIFEST_SIGNING_PUBLIC_KEY_BASE64` from the approved trust-anchor record. For an off-host drill, also inject `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and optional `AWS_SESSION_TOKEN` into the current process from the approved secret store, omit `-DryRun`, and keep `-ArtifactSource S3`. To select one immutable object explicitly, add:

```powershell
-OffHostArtifactKey shamrai/daily/shamrai-db.YYYYMMDDTHHMMSSZ.dump.age
```

The key must match the configured prefix and generated timestamped daily key format; traversal-like or unrelated keys are rejected. Off-host and VDS selection use signature commit markers, not orphan ciphertext or manifest uploads. Schema v1/v2 and unsigned legacy copies are intentionally rejected by this protected drill. The restore remains isolated and still requires explicit SSH access to the canonical target; it never changes production by default.

GitHub Actions runs the S3-source drill weekly via `.github/workflows/restore-drill.yml`. A manual `workflow_dispatch` can select `artifact_source=vds` or `artifact_source=s3` and optionally provide `off_host_artifact_key`; only the S3 job step receives the off-host credential secrets.

Do not rotate the signing key as part of a normal backup, credential refresh, bootstrap rerun, or deploy. The installer deliberately reuses an existing encrypted signing credential and refuses to replace it. A future rotation must first make both old and new public keys available to the exact-SHA restore code, then switch the VDS signer, and retain the old trust anchor until every old S3 object version has passed the 90-day retention window. The current single-key implementation therefore requires a dedicated multi-key rotation change before replacing the key.

## Manual Production Restore

Only run this during an explicit maintenance window. This restores the canonical production database and must not touch system nginx or unrelated containers.

1. Create a fresh pre-restore backup:

```bash
cd /opt/shamrai-mini-app
install -d -m 0700 /opt/shamrai-mini-app/db-backups/manual
docker compose -p shamrai exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' > "/opt/shamrai-mini-app/db-backups/manual/pre-restore-$(date -u +%Y%m%dT%H%M%SZ).dump"
chmod 0600 /opt/shamrai-mini-app/db-backups/manual/pre-restore-*.dump
```

2. Decrypt the chosen encrypted backup on the operator machine:

```powershell
age -d -i C:\Users\Sa1z1ngr0z\.config\age\shamrai-backup-identity.txt -o .\.deploy\manual-restore.dump .\.deploy\backup.dump.age
```

3. Upload it to the VDS as a temporary file:

```powershell
scp -i C:\Users\Sa1z1ngr0z\.ssh\codex_deploy_ed25519 .\.deploy\manual-restore.dump root@82.147.67.245:/tmp/shamrai-manual-restore.dump
```

4. Restore and restart only Shamrai app services:

```bash
cd /opt/shamrai-mini-app
chmod 0600 /tmp/shamrai-manual-restore.dump
docker compose -p shamrai stop backend frontend
docker compose -p shamrai exec -T postgres sh -c 'pg_restore --clean --if-exists --no-owner --role="$POSTGRES_USER" --exit-on-error -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < /tmp/shamrai-manual-restore.dump
rm -f /tmp/shamrai-manual-restore.dump
docker compose -p shamrai up -d backend frontend
docker compose -p shamrai ps
curl -fsS http://127.0.0.1:8082/api/health
```

## Failure Triage

- Backup fails before encryption: check `docker compose -p shamrai ps`, Postgres health, disk space, and `/opt/shamrai-mini-app/ops/backup.log`.
- Backup fails at encryption: check `age` is installed and `/opt/shamrai-mini-app/ops/backup.env` has a real `SHAMRAI_BACKUP_AGE_RECIPIENT`.
- Manifest signing fails: keep the unsigned files quarantined, confirm the systemd service loaded `manifest_signing_private_key`, and compare only public-key SHA-256 values. Never print, decrypt to disk, or copy the private key into a ticket.
- Off-host upload fails after local commit: preserve the local bundle, check the non-secret endpoint/bucket/prefix configuration, confirm the scheduler injected the AWS credentials and signing-key file path, and inspect the provider audit log. Never print or copy credential values into the ticket.
- No recent off-host signature: treat ciphertext or a manifest without its matching `.manifest.sig` as uncommitted; investigate alerting, bucket lifecycle, versioning/Object Lock status, and the backup process exit code.
- Off-host metadata/hash mismatch: quarantine the selected object version, retain provider audit evidence, and drill an older committed version. Do not rewrite or delete the suspect version with the backup identity.
- Restore drill signature/binding/hash mismatch: treat the selected bundle as untrusted; retain the immutable object versions and provider audit evidence for investigation. Do not automatically fall back to an older backup.
- Restore drill count mismatch: the dump restored but data does not match the manifest; do not trust that artifact.
- Backend does not start in drill: inspect temporary backend logs before rerunning with cleanup, then compare app env requirements against the restore-drill Compose environment.
- Production health fails after drill: the drill should not mutate production. Check `docker compose -p shamrai ps`, canonical port `8082`, and recent production logs before touching nginx or unrelated services.
